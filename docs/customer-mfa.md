# Customer TOTP MFA

## Deployment and configuration

This feature adds customer-only MFA and does not replace admin authentication.
Apply the additive migration `20260906000000_customer_mfa` before serving the
updated app (`npx prisma migrate deploy`). Do not reset the database. Existing
users have no MFA row until needed, equivalent to MFA disabled/version zero.
The migration adds only `customer_mfa` and `customer_mfa_challenges`, with foreign
keys to users. It was tested by applying the full migration history to an empty,
isolated local PostgreSQL database; no production migration was run during development.

Runtime: the locked OTPAuth dependency requires Node.js 20.19 or later.

Required server environment:

- `MFA_ENCRYPTION_KEY`: exactly 64 hexadecimal characters (32 random bytes).
  Generate with `openssl rand -hex 32` and put the result directly in the hosting
  provider's secret store. Never prefix with NEXT_PUBLIC, commit, or log it.
- `NEXTAUTH_SECRET`: existing session-signing secret; keep it strong and stable.
- `NEXTAUTH_URL`: the canonical HTTPS application origin. MFA mutations require
  the browser's Origin header to match it; configure preview environments with
  their own correct origin.
- Existing `DATABASE_URL` / `DIRECT_URL` and Google OAuth credentials.
- Existing `GMAIL_USER` / `GMAIL_APP_PASSWORD` for security notification emails.

Missing/malformed MFA_ENCRYPTION_KEY prevents enrollment, verification, disabling,
and regeneration. MFA-enabled primary login fails closed. Non-MFA login remains
available. Existing fully verified sessions remain subject to normal expiry and
MFA-version checks; they do not need decryption for ordinary requests.

Back up the encryption key separately from the database. Losing it makes TOTP
secrets unreadable. Do not simply replace it: coordinated rotation must decrypt
with the old key and reencrypt every secret with the new key while MFA writes
are paused. Automated multi-key rotation is not part of this change.

## Enrollment and management

Account → Security shows disabled, setup-in-progress, and enabled states.
Enrollment requires a full customer session and current-password confirmation.
Google-only accounts require a Google primary authentication within five minutes;
a recent MFA completion does not refresh an older primary authentication time.
Old NextAuth sessions without an authentication timestamp cannot authorize changes.

The server generates a 160-bit TOTP secret using OTPAuth. Provisioning uses
SHA-1, six digits, and a 30-second period for broad authenticator compatibility.
The QR code is generated by the server, with no third-party QR service. Only the
initial provisioning response exposes the manual key/QR. Setup expires after
five minutes. Generating the QR does not enable MFA; a valid code is required.

Secrets are stored as versioned AES-256-GCM ciphertext with random 96-bit IVs,
128-bit tags, and user-specific authenticated data. Recovery codes contain 128
random bits each; PostgreSQL stores only SHA-256 hashes. Ten codes are shown once
after enabling/regenerating. The user must explicitly acknowledge saving them.
If the response is lost or the user leaves without saving, MFA stays enabled;
a valid authenticator and primary reauthentication can regenerate the codes.
Status APIs expose counts/booleans, not ciphertext, hashes, codes, or provisioning keys.
Sensitive responses use no-store; browser storage never holds MFA material.

Disabling and regenerating require current-password confirmation (or recent
Google-only primary authentication) and TOTP/an unused recovery code. Both
invalidate outstanding challenges and other customer sessions. Regeneration
replaces all old recovery hashes; disabling erases secrets and recovery hashes.
Enrollment also invalidates pre-MFA customer sessions.

## Login and database guarantees

Password login verifies bcrypt before consulting MFA. Google login and the legacy
OAuth bridge verify NextAuth identity before consulting the same MFA service.
MFA-enabled accounts receive only a five-minute, random HTTP-only/SameSite=Strict
challenge cookie. Only its hash is stored in PostgreSQL. No customer cookie is
issued until the second factor succeeds. Registrations create new accounts only;
existing accounts cannot use registration to bypass MFA. Password reset does not
disable MFA or issue a session.

All MFA mutations lock the customer's PostgreSQL user row. TOTP verification
accepts at most one step of skew, tracks the highest used step, and rejects
replay. Recovery-code removal and challenge consumption commit in the same
transaction. Account-wide limits allow ten MFA/challenge/management attempts
per fixed 15-minute window, including failures. Starting new challenges does
not reset the budget. Repeated failures return generic errors or 429.

Custom customer cookies include an MFA version and signed second-factor proof.
Every getCurrentUser call compares them with current database settings and
rejects archived users. MFA enable/disable/regeneration increments the version.
Old signed cookies and first-factor-only cookies cannot bypass enabled MFA.
Admin-cookie validation is unchanged. No client-side guard supplies authorization.

## Lost authenticator and notifications

Use a recovery code to log in, then use another code plus primary reauthentication
to disable/re-enroll, or regain access to the authenticator and regenerate codes.
If both factors are lost, there is deliberately no self-service/email-only MFA
removal. Contact support; do not reset MFA based only on email, password reset,
or order details. There is no support-reset endpoint in this implementation.
Without a separately approved identity-proofing process, the account remains locked.

The existing mailer attempts security emails for enable, disable, regeneration,
and recovery-code use. No secret/code appears in messages or logs. Delivery is
best effort with the mailer's existing retries; failures are logged without
sensitive data. There is no durable notification outbox in this change.

## Tests

`src/lib/mfa/crypto.test.ts` runs without a database and includes the RFC 6238
SHA-1 vector, skew/replay checks, encryption tampering/binding, key validation,
and recovery-code generation.

`src/lib/mfa/security.test.ts` runs against a disposable local PostgreSQL database
named `repixl_mfa_test`. It deletes users in that database between tests. It mocks
only NextAuth, Next cookie I/O, and email delivery; customer authorization,
Prisma transactions, bcrypt, encryption, TOTP, and API routes are real.

```sh
# Create an empty local repixl_mfa_test database first.
export TEST_MFA_DATABASE_URL='postgresql://postgres:local-test-only@127.0.0.1:55440/repixl_mfa_test?connection_limit=12'
DATABASE_URL="$TEST_MFA_DATABASE_URL" DIRECT_URL="$TEST_MFA_DATABASE_URL" npx prisma migrate deploy
npm test
npm run build
```

Integration tests skip unless TEST_MFA_DATABASE_URL is supplied; they never use
application DATABASE_URL as a fallback. Purchase-concurrency tests can run in
parallel with their own separate TEST_DATABASE_URL database.
